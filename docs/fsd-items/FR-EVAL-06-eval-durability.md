# FR-EVAL-06: an evaluation must survive a deploy

**State as of 2026-10-12.** An evaluation runs entirely in the api process's memory (`services/api/internal/jobs/runner.go`), takes 30-50 minutes per posting and 5-6 hours for a ten-posting set (`docs/evaluation.md:54-55`), and is killed outright, with no resume, whenever that process exits. The only control in place is `/admin/ops`, which lets a human check whether a run is in flight before choosing to deploy; nothing in the deploy path itself checks, and nothing persists enough state to resume a killed run. What does survive is the per-posting results already written to Postgres, recovered into the run's summary counters at the next boot by `FailStrandedEvalRuns` - but that is a post-mortem accounting of a run that was still destroyed, not a run that kept going.

## What the FSD requires

FR-EVAL-06, `docs/FSD.md:525`: "An evaluation shall not be silently destroyed by a deploy." Status: **Must (partially Shipped)**. The FSD's own note on the row: "The job runner keeps jobs in memory, so recreating the api container kills a run. `/admin/ops` (FR-ADM-19) answers whether one is in flight, which is the control today. All three services share one `IMAGE_TAG`, so there is no partial deploy that avoids this; per-service tags are in the backlog."

## What exists today

- **The job runner holds everything in memory.** `jobs.Runner.jobs` is a `map[string]*Job` guarded by a mutex (`services/api/internal/jobs/runner.go:134-141`); each job runs as its own goroutine (`runner.go:190`, `go r.run(j, timeout, fn)`). The package comment is explicit about the trade-off: "State lives in memory: a restart forgets running jobs, which is acceptable because every job here is idempotent and can simply be started again" (`runner.go:1-7`). That acceptability judgment was made for corpus reindexes and embed sweeps, which cost minutes; an evaluation inherited the same mechanism and costs hours.
- **An evaluation is one such job.** `RunJob` dispatches `JOB_KIND_EVAL_QUICK` to `a.evaluator.Run` (`services/api/internal/handlers/admin_jobs.go:98-110`), started via `a.jobs.StartWithin(kind.String(), jobTimeout(kind), fn)` (`admin_jobs.go:145`), with `jobTimeout` giving it an 8-hour ceiling (`admin_jobs.go:42-45`) - comfortably above the 5-6 hour documented runtime for ten postings.
- **Per-posting results are durable; the run's own bookkeeping is not.** The evaluator writes one row per posting via `RecordEvalItem` as it scores each one (`services/api/internal/users/golden.go:250-266`), and that lands in Postgres immediately. But the running tally (`scored`, `errors`, `gate_correct`, `margin`) lives only in the evaluator's local variables until `FinishEvalRun` is called at the end (`golden.go:268-282`). Kill the process mid-run and the `eval_runs` row is still sitting at whatever it was set to on `StartEvalRun` (`golden.go:207-227`), which defaults `status` to `'running'` (`services/api/internal/db/migrations/00027_golden_set.sql:47`).
- **`FailStrandedEvalRuns` recovers the accounting, not the run.** Called at boot from `cmd/api/main.go:399`, right after `FailStrandedJd` and `FailStrandedRuns` reconcile the equivalent state for JD and plain runs (`main.go:383-401`). It closes any `eval_runs` row still at `status = 'running'` with `finished_at IS NULL`, and recomputes `scored`, `errors`, and `gate_correct` by counting the `eval_items` rows that did land, rather than trusting the dead goroutine's last known tally (`services/api/internal/users/golden.go:303-321`). The doc comment is direct about why: "Run 14 was stopped after five of nine postings and its row read 'scored 0, errors 0' while five eval_items sat beside it. The work was done and the summary of it was thrown away, which is the wrong half to lose" (`golden.go:287-291`).
  - **`margin` is deliberately left out of the recovery.** The function updates `status`, `note`, `scored`, `errors`, `gate_correct`, and `finished_at`, but not `margin` (`golden.go:304-316`). The comment states the reasoning in full: "margin is deliberately left alone. It is only comparable when every posting scored, so computing one for a partial run would produce a number that invites exactly the comparison it cannot support" (`golden.go:299-301`). FR-EVAL-09's FSD row quotes the same reasoning verbatim (`docs/FSD.md:528`).
- **There is no cancel RPC.** Confirmed by both the code (no `Cancel*` method anywhere in `admin_jobs.go` or `runner.go`) and the doc comment on `FailStrandedEvalRuns`: "There is no cancel RPC, so stopping a run means restarting the api... and that is exactly the path that skips the close" (`golden.go:293-295`). The only way to stop a run is to kill the process - the same action a deploy takes.
- **`/admin/ops` reports what is in flight, for a human to read before deciding.** `GetOpsStatus` lists recent jobs from the in-memory runner and sets `out.Busy = true` for anything without a `FinishedAt` (`services/api/internal/handlers/admin_ops.go:38-56`); separately it reports `LatestEval` from the `eval_runs` table (`admin_ops.go:80-90`), which, being table-backed, "survives the restart that empties the runner" (comment at `admin_ops.go:58-59`). This is the whole of FR-ADM-19 as it pertains to evaluations: visibility, not prevention. The FSD's own characterization is "the control today" (`docs/FSD.md:525`), not a safeguard.
- **`rollout.sh --only <service>` is the one mechanism that actually prevents the kill**, and it already exists, just not automatically applied. `deploy/rollout.sh:36-47` explains it was added because "all three services shared one `IMAGE_TAG`, so `compose up -d` recreated the api for a CSS change and killed any evaluation in flight," and names the incident: "a one-line front-end fix therefore waited on a five-hour run four times on 2026-09-29." With `--only web`, the compose command only recreates the web container (`rollout.sh:150-160, 188`), leaving api (and any eval goroutine) untouched. The script's `--only` validates against `web|api|sidecar` (`rollout.sh:59-62`) - it has no special knowledge of evaluations; it is a general per-service deploy, and the operator has to know to reach for it.

## What is missing

1. **No automated check for an in-flight evaluation anywhere in the deploy path.** `rollout.sh`'s `quiet_check` (`rollout.sh:95-124`) queries only two things: `dt_sessions` with `status = 'running'` started in the last 25 minutes, and a count of rows in `events` in the last 10 minutes. Neither touches `eval_runs` or the job runner. **This matters more than it looks**: the `events` table (`services/api/internal/db/migrations/00023_events.sql:8-26`) is client/product telemetry - page views, logins, chat - not server-side evaluation processing. An evaluation generates, at most, one event when an admin clicks "start" on `/admin/evals`; the following five hours of judge calls write to `llm_usage` and `eval_items`, not `events`. So an evaluation at minute 11 of a 5-hour run is already invisible to `quiet_check`'s "recent events" heuristic - it is not a near-miss protection, it is no protection.
2. **No automatic selection of `--only web` for front-end-only changes.** The capability exists; nothing in CI or `rollout.sh` inspects the diff to decide a full rollout isn't needed. An operator doing a full `deploy/rollout.sh <sha>` for a change that happens to touch only `apps/web` will still recreate api and kill a running eval, exactly as before the incident that `--only` was built to fix.
3. **No persistence or resume for the run itself.** Nothing records which goldens in a run have already been scored in a form the evaluator reads back on restart; `Evaluator.Run` (`services/api/internal/jd/evaluate.go:66`) walks `ListGoldenPostings` fresh every time with no notion of "already done in run N." A restarted api cannot pick a killed run back up - it can only, at best, start a new one.
4. **No graceful-shutdown handling.** Nothing in `cmd/api/main.go` or the runner traps `SIGTERM` to let an in-progress posting finish and checkpoint before the container is killed; neither `docker-compose.yml` nor `docker-compose.prod.yml` sets a `stop_grace_period` for `api`, so `docker compose up -d` recreation falls back to Docker's default 10-second stop timeout - far shorter than even one LLM judge call, let alone a posting.
5. **No per-service `IMAGE_TAG`.** The FSD row names this directly as the structural reason there is "no partial deploy that avoids this," and files it as backlog (`docs/FSD.md:525`). Today the workaround is the operator remembering `--only`.

## Why this is harder than it looks

The obvious-looking fix, "just don't recreate the api container while an eval is running," collides with the fact that *the only way to stop a run is to kill the api*, and *the only way to ship an api change is to kill the api*. There is no daylight between "deploy" and "kill" for this process: no cancel RPC, no checkpoint, no SIGTERM handler, no separate worker process that could keep an eval alive while the request-serving process restarts. Any fix that does more than add a check has to introduce one of: (a) a way to pause/resume an evaluation across a process restart, which means checkpointing which postings are done and teaching the evaluator to skip them on restart; (b) a way to keep the evaluation's goroutine alive independent of the api's HTTP lifecycle (a separate worker process, which is a real architectural change, not a patch to `rollout.sh`); or (c) accepting that evaluations and api deploys are mutually exclusive and enforcing that mechanically, which is a control, not a fix, and still loses whatever the quiet_check above already fails to catch for decision tests: a run killed mid-flight is still gone, only now by policy rather than by accident.

There is also a subtlety in what "surviving a deploy" should even mean here. FR-EVAL-09 (Shipped, `docs/FSD.md:528`) already guarantees that a killed run's *completed* postings are not lost - `FailStrandedEvalRuns` recovers them. FR-EVAL-06 as worded ("shall not be silently destroyed") could be read as satisfied by that recovery alone, but the FSD maintainers evidently don't read it that way, since FR-EVAL-06 is still only "partially Shipped" while FR-EVAL-09 is "Shipped." The distinction that justifies treating them differently: FR-EVAL-09 answers "what happens to the work already done," which is a data-loss question answered by `FailStrandedEvalRuns` reading `eval_items`. FR-EVAL-06 answers "does the run keep going," which is a liveness question that nothing today answers - a killed run does not resume, it is recorded as failed with partial credit. Conflating the two would make FR-EVAL-06 look done when the thing it actually asks for (a run not being destroyed at all) still isn't built.

## Dependencies and constraints

- Single `IMAGE_TAG` across `web`, `api`, `sidecar` in `.env.prod` (`deploy/rollout.sh:11-15, 34`) means any full rollout recreates all three regardless of what changed, unless `--only` is used deliberately.
- `jobTimeout` already caps an `EVAL_QUICK` job at 8 hours (`admin_jobs.go:43-44`); any resume design has to either preserve that ceiling across a restart or re-derive it.
- The evaluator reuses the ordinary submission pipeline per posting (`services/api/internal/jd/evaluate.go:17-26` - "it runs each posting through the ordinary pipeline rather than a special one... the cost is that an evaluation takes as long as the set does"), so a resumable design inherits whatever retry/idempotency behavior that pipeline has for a posting interrupted mid-judgment, which was not examined here.
- `margin`'s null-on-partial-run rule (`golden.go:299-301`) is a constraint any new recovery or resume path must keep respecting: a resumed run that finishes should compute margin normally, but if a resumed run is itself interrupted again, the same "don't compute it for a partial run" rule applies.

## Options, with their trade-offs

1. **Extend `quiet_check` to also query `eval_runs` for `status = 'running'`.** Cheap - the same pattern as the existing `dt_sessions` query, one more `psql -Atc` call in `rollout.sh`. Blocks (or, with `--force`, warns through) a deploy while a real evaluation is in flight. Does not help a `--only web`-eligible change get *chosen* automatically, and does nothing for the api itself: if the change being shipped *is* an api fix, the operator is still stuck choosing between shipping now (killing the eval) or waiting hours. Pure control, not a fix; this is explicitly the category FR-EVAL-06's current partial-Shipped note already describes as "the control today," just moved from a human reading `/admin/ops` to the script enforcing it.
2. **Auto-detect a web-only diff and default to `--only web`.** Moderate: needs `rollout.sh` (or a wrapper) to diff the target SHA against the currently-deployed tag and restrict to `apps/web` paths before deciding scope. Removes the "operator forgot to pass `--only`" failure mode that caused the four repeated five-hour waits on 2026-09-29. Still does nothing when the change actually touches the api.
3. **Per-service `IMAGE_TAG`s, built out of the backlog item the FSD already names.** Decouples what gets rebuilt in CI from what gets redeployed; combined with option 2 this makes "ship the front end without touching the api" the default path rather than an opt-in flag. Infrastructure work across CI and `.env.prod` handling; does not by itself solve an api-side fix landing while an eval runs.
4. **Checkpoint and resume the evaluation itself.** The real fix for the liveness half of FR-EVAL-06. Requires: a way for `Evaluator.Run` to ask "which goldens in this `eval_run_id` already have an `eval_items` row" and skip them (the data for this already exists - `eval_items` is written per-posting, `golden.go:250-266`); a `SIGTERM` handler in `cmd/api/main.go` that lets the current in-flight posting finish (or stops cleanly between postings) before the process exits; a longer `stop_grace_period` on the api service in both compose files, generous enough to cover one posting's judge calls; and a decision on whether resume happens automatically at next boot (symmetrical with `FailStrandedEvalRuns`, but resuming instead of closing) or requires an admin to explicitly restart the run. This is real engineering, not a script change, and touches the deploy compose files, `cmd/api/main.go`, the evaluator, and probably the `eval_runs` schema (a resumable run needs to record more than "running/done/failed" if "paused, resumable" is a distinct state).
5. **Move the job runner out of the request-serving process entirely.** A separate long-running worker (or sidecar) that holds jobs, survives api deploys by construction, and the api process just submits to it and polls. Removes the problem at the architecture level rather than mitigating it, but is a genuine new service with its own deploy lifecycle, failure modes, and - notably - its own version of this exact question ("what happens to a job when the worker itself needs to deploy"), so it does not eliminate the need for option 4's checkpoint/resume logic, it just relocates where that logic has to live.

## Decisions the owner must make

- Is a deploy-time check (option 1, possibly 2) sufficient to call FR-EVAL-06 "Shipped," or does the requirement's wording ("shall not be... destroyed") require resume (option 4) before it can move off "partially"? The FSD's own distinction between FR-EVAL-06 and the already-Shipped FR-EVAL-09 suggests the maintainers intend the stronger reading, but that is this document's inference, not a recorded decision.
- Is it worth building per-service `IMAGE_TAG`s (option 3) now, or only if/when api-side changes start colliding with evaluations as often as front-end ones did before `--only` existed?
- If checkpoint/resume (option 4) is pursued, should a resumed run be triggered automatically at boot (mirroring `FailStrandedEvalRuns`'s existing automatic recovery) or require an explicit admin action, given that automatic resume of a multi-hour LLM job on every restart has its own cost and failure surface?
- How much `stop_grace_period` is enough, given a single posting at the pipeline's own documented worst case (`docs/evaluation.md` describes an incident where a posting ran four hours before aborting) - and whether that worst case should instead be treated as a pipeline bug rather than something the deploy path needs to wait out.

## Task checklist

- [ ] Add an `eval_runs`-status check to `rollout.sh`'s `quiet_check`, alongside the existing `dt_sessions` query, with the same `--force` override.
- [ ] Decide and document whether a web-only diff should auto-select `--only web`, and implement if so.
- [ ] Scope and prioritize per-service `IMAGE_TAG`s against other backlog items (FSD already tracks this as backlog, not newly discovered here).
- [ ] Design the resumable-run data model: what `eval_runs.status` values distinguish "stopped and closed" (today's `FailStrandedEvalRuns` behavior) from "stopped and resumable," and how the evaluator queries already-scored goldens for a given `eval_run_id`.
- [ ] Add a `SIGTERM` handler to `cmd/api/main.go` and set an adequate `stop_grace_period` for the `api` service in `docker-compose.yml` and `docker-compose.prod.yml`.
- [ ] Decide automatic vs. admin-triggered resume at boot, and implement alongside (or as a variant of) `FailStrandedEvalRuns`.
- [ ] Re-grade FR-EVAL-06 in `docs/FSD.md` only once an actual prevention or resume mechanism ships; today's row text already describes the current state accurately and should not be changed as part of documentation work alone.

## What could not be verified

- Whether anyone currently, as a matter of practice, checks `/admin/ops` before every deploy. That is an operational habit, not something the repository records; FR-ADM-19's existence is verified, its consistent use is not.
- The exact Docker-reported stop/kill timeout actually experienced in production (this document infers the 10-second Compose/Docker default from the absence of `stop_grace_period` in both compose files, but did not test a live container shutdown to confirm no other override applies, e.g. at the Docker daemon or systemd-unit level on the host).
- Whether the ordinary submission pipeline that the evaluator reuses per posting (`jd/evaluate.go`) is itself safely re-runnable for the same posting without side effects (duplicate submissions, duplicate LLM spend already billed) - relevant to option 4's resume design but out of scope for this survey, which only confirmed that `RecordEvalItem`'s `ON CONFLICT (eval_run_id, golden_id) DO UPDATE` (`golden.go:256-259`) makes re-recording a given posting's result idempotent at the storage layer.
- Whether `docs/evaluation.md`'s four-hour aborted-posting incident (referenced in "Why this is harder than it looks") has since been fixed by the schema-bounding work described in FSD changelog 0.3.11 (FR-JD-15, `docs/FSD.md:31`); this document cites the incident only to establish that posting duration has a documented long tail, not to characterize current reliability.
